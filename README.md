# glassmind

A system you talk to about Rust code, short stories, everyday requests, facts and quantities,
with **no LLM at runtime**. Typed Rust code reasons and checks actions;
small inspectable models propose interpretations. The coding frontend can
show the trace behind its answers (`--explain`).

Codex GPT-6 Astra fast workers build it through the user's logged-in
ChatGPT account, without API keys. A measured improvement loop keeps useful
changes. The original code-QA data was generated by Claude Opus 5.5; new
tracks use outside benchmarks including CLINC150 and bAbI. Development
scores select changes; official test splits are reported as totals only.

## Using it

```sh
cargo build --release
# ask about a repository (name=path, repeatable; defaults to the current directory)
./target/release/glassmind ask -s tds=../top_down_shooter_game "which functions call spawn_wave?"
# the full trace: words, parse, meaning, references, dropped readings, reply rules and their rounds
./target/release/glassmind ask --explain -s tds=../top_down_shooter_game "what calls spawn_wave"
# talk interactively; Tab offers what can come next, including real names
./target/release/glassmind chat -s tds=../top_down_shooter_game --session talk.json
# machine-readable outcome
./target/release/glassmind ask --json -s tds=../top_down_shooter_game "what calls spawn_wave"
# what may come next after an unfinished input
./target/release/glassmind complete -s tds=../top_down_shooter_game "which functions call spa"
```

Edits are proposed as a set of changes and applied only with `--apply`; it
never commits.

As a coding agent (it runs `cargo check`, `cargo test` and `clippy` itself,
in a memory-capped scope, and reads their messages). Build and lint checks
continue across independent targets so one failure does not hide other diagnostics:

```sh
# talk about a crate, its build and its tests; "yes" applies a proposed fix
./target/release/glassmind code ../some-crate
# act on one request: a fix or edit it finds is made, anything else is printed
./target/release/glassmind do ../some-crate "the build is broken, fix it"
# add an explicit scalar field and update resolved constructors, with tests and rollback
./target/release/glassmind do ../some-crate "Add pub weight: u16 to Parcel. Use 7 for all existing constructors."
# as the agent of the rustbench benchmark (github.com/gold-silver-copper/rustbench)
rustbench run --agent ./tools/rustbench-agent.sh
```

Explicit kinds help with names that are also English words: `where is function called?`
and `rename function weigh to called`. Code notation preserves significant
underscores: `renamed_()` refers to `renamed_`.
[Identifier scope and verification](tools/coding-identifier-roles/PARENT.md).
An explicitly selected struct field can also be renamed when other structs use
the same field name. Resolved declarations, literals and typed parameter accesses
change together; unsupported bindings refuse.
[Field ownership and independent review](tools/coding-field-owners/PARENT.md).

## Conversation and story commands

```sh
# Memory, arithmetic, units and dates; no model needed
./target/release/glassmind talk --session conversation.json
# Calculations also work within the same conversation
printf '%s\n' 'Convert 1/3 hours to minutes' | ./target/release/glassmind talk
# Add learned everyday-intent recognition after training (services are not connected)
bash crates/everyday/tools/reproduce.sh
./target/release/glassmind talk --model scratch/everyday/intent.json --session conversation.json
# Add an offline facts bundle, prepared with tools/facts/chat/package.py
./target/release/glassmind talk --facts-dir scratch/facts-bundle --session conversation.json
# Follow assertions and answer questions about a short story
./target/release/glassmind-stories --model tools/stories/action-model.json
# Exact arithmetic, typed units and calendar dates
./target/release/glassmind-quantities "Convert 60 km/h to m/s"
```

For example, `glassmind talk` remembers “my name is Mira”, answers “what is
my name?”, and applies “actually, my name is Jo”. Story input uses one
assertion or question per line; `/reset` starts a new story.
An unrelated turn clears the target of a bare correction such as “actually, it's coffee”.
Name the field explicitly to correct it, or ask about that field first. A learned
name-change request without a usable name leaves memory unchanged.
[Memory behavior and verification](tools/conversation/memory-authority/PARENT.md).
A complete social turn such as “see you later” preserves story state. Unsupported
appended assertions still invalidate stale answers.
[Conversation routing checks](tools/conversation/route-authority/PARENT.md).
Buffered model loading reduced fresh-process startup from 2.59s to 0.093s in a
[local paired probe](tools/conversation/buffered-loading/PARENT.md), with unchanged replies.
[Dialogue tracking](crates/dialogue/EXPERIMENT.md) has a separate trained-model
command. [Local Wikidata bundles](tools/facts/chat/HANDOFF.md) can also answer
questions in `talk`: replies include source links, and JSON includes entity IDs
and provenance. Bundles declare their own asset hashes and coverage; labels
affect display only. Ordinary memory, calculation and story questions keep their
existing priority. For multiple matches, use `List answers to: Who wrote TITLE?`.
[Explicit factual lists](docs/fact-sets.md) return up to ten sorted matching IDs,
source links and local match counts, while preserving personal and story state.
The demonstrated bundle is a finite 500-entity snapshot with known errors.

Scalar word problems can combine fractions, percentages, sums and comparisons
in multiple clauses. Glassmind solves exact constraints and requires a unique
requested value; ambiguous differences refuse, while explicit subtraction stays
ordered. This adds six correct MathQA dev answers with existing answers preserved.
[Scope, independent checks and semantic review](tools/quantities/linearwords/PARENT.md).

## How it is built

Three layers, kept apart by the crate graph (`cargo run -p glassmind-depcheck`, run by loop checks):

| crate | layer |
|---|---|
| `glassmind-meaning` | language-neutral, data-neutral meaning types, and the `Language` / `World` interfaces |
| `glassmind-grammar` | the grammar's fixed building blocks: an Earley parser that carries meaning values, reads left to right, keeps every reading, reports where it got stuck and what may come next; and the same rules run backwards to speak |
| `glassmind-english` | English: tokenizer (the only code that reads raw text), categories, phrase values, rules, function words, replies |
| `glassmind-world-rust` | the Rust world: items, kinds, relations, `syn` indexing, lookup, answering |
| `glassmind-english-rust` | English words for the Rust world's kinds and relations |
| `glassmind-mind` | dialogue: readings, name resolution, preference rules, sessions, traces |
| `glassmind-rules` | every rule's stable ID, the loop round that added it, and runtime switches |
| `glassmind-models` | small learned models (the normalizer's edit model, the request-category tagger) and their held-out reports: they propose and rank, typed code decides |
| `glassmind` (cli) | `ask`, `chat`, `code`, `do`, `complete`, `eval`, `rules`, `train-normalizer`, `train-intents` |
| `glassmind-loop` | the scorer (with its own cargo runner for judging fixes), the size counter and the improvement loop |
| `tools/oracle` | computes exact answers with `syn`, independently of glassmind |
| `tools/datagen` | plans conversations from tasks and phrases them with ChatGPT-authenticated Codex GPT-6 Astra fast |

The meaning layer depends on no language and no world; English depends on
no world; worlds depend on no language.

## Data and scoring

1. `tools/oracle` picks tasks in real repositories at fixed commits and
   computes their exact answers (`docs/tasks.md` is the contract).
2. `tools/datagen/plan.py` builds conversations backwards from tasks:
   single requests, follow-ups that say "it", corrections, context
   requests, "why" after an edit, user-defined nicknames.
3. `tools/datagen/phrase.py` phrases them in several styles (prompt
   families: terse, chatty, newcomer). A different prompt family writes
   the held-out set, about repositories never used in training.
4. `tools/datagen/finish.py` checks every turn with tooling and an LLM
   checker and writes `inputs.jsonl` and `labels.jsonl`.
5. `glassmind-loop score` compares outcomes with labels: right costs 0, a
   refusal 0.5 to 1 depending on how far it got, a confident wrong answer 10.

## The loop

`glassmind-loop run --state DIR` (or `tools/loop-service.sh start DIR` to
run it as a detached, resumable service) supports:

- **growth rounds**: group the training failures, start capped Codex GPT-6 Astra fast
  workers using the ChatGPT login, each in its own git worktree inside a bubblewrap
  sandbox that hides the held-out data, with one failure group, examples,
  and an earlier accepted change;
- **compression rounds** (disabled while growing fast): switch every rule used by at most one right
  answer off by its ID, and brief an agent to delete what nothing needs and
  merge or generalize the rest.

A change is accepted only if it builds and passes fmt, clippy and the
layer check; lowers training cost (the code-size price is currently zero); turns no right or honestly refused training turn wrong; does not
worsen the validation score (other repositories, when configured) by more than 2; and is not
vetoed by a reviewer agent for faked answers. The held-out score decides
nothing, not even when to stop: it is only reported. Agents cannot read
anything held out, and the scorer's code (`crates/loop`, `crates/answer`)
is outside what they may change. Every check on code runs in a
memory-capped scope that ends everything it started.

CI runs `tools/check.sh`: fmt, clippy, build and one fixture smoke, in a
memory-capped scope. The smoke gate requires every fixture turn to be correct
and rejects an empty evaluation. Full development runs happen per track before pushing
a feature batch, rather than after every edit.

The [SQuAD2 baseline](tools/reading/qa2/README.md) separates substantive answers
from expected refusals. Its official selected EM is46.95%, below an always-refuse
comparator. One prediction ofA receives official normalization credit despite
being a wrong substantive answer; the table and separate diagnostic retain it
as wrong. No new reading model is deployed.
